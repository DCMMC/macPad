# iPad14,3 / iPadOS 16.5.1 port — 2026-10-06

This note records the exact identities and fail-closed deployment observations
for an iPad14,3 running iPadOS 16.5.1 (20F75), using the existing Ventura 13.4
(22F66) filesystem. It intentionally contains no address, password, hostname,
or other user-specific credential.

## Rootless `/var/jb/usr` exposure recovery

The first bounded workspace start stopped safely before launching WindowServer:

```text
MacWS: refusing to cover nonempty /var/mnt/rootfs/var/jb/usr with a bind mount
```

Read-only inventory found only a legacy DockHelperProxy copy and three legacy
ElleKit/Substrate paths in that directory. The two live binaries differed from
their current `/var/jb/usr` counterparts. The exact old directory was preserved
as `usr.macws-prebind-20261006`, then an empty exposure point was provisioned.
No user data was deleted.

Runtime-confirmed via the packaged `mount_bindfs` output on this kernel:

```text
exposed /var/jb/usr at /var/mnt/rootfs/var/jb/usr via symlink (bind unsupported on this kernel)
```

The helper creates the exact absolute link `/var/mnt/rootfs/var/jb/usr ->
/var/jb/usr`. The former mount-only idempotence check subsequently followed the
link, saw the live source contents, and rejected its own valid fallback. The
boot helper now accepts only that exact source link and only when the packaged
Dock XPC proxy is executable through it. Any other link, a missing proxy, or an
arbitrary nonempty directory still fails closed.

## AGX selector-0x100 ABI change

The next bounded start reached WindowServer, but the exact process crash looped
during AGX initialization. Runtime-confirmed via
`WindowServer-2026-10-06-080317.ips`:

```text
EXC_BAD_ACCESS / KERN_INVALID_ADDRESS at 0x8
AGX::Device<...>::~Device() +2504
-[AGXG13GFamilyDevice initWithAcceleratorPort:simultaneousInstances:] +9228
```

The matching stderr supplies the upstream failure before that cleanup crash:

```text
AGX: agxa_device_template.hpp:599:setupImmediate:
IOConnectCallStructMethod with selector 256 failed. 3758097090:
(iokit/common) invalid argument
```

The existing adapter unconditionally changed Ventura's 0x78-byte output to the
0x70 bytes required by the older validated kernels. An iOS-native, read-only
probe against the real 20F75 AGX user client isolated the ABI boundary:

```text
sel=0x100 requested=0x68 returned=0x68 -> kr=0xe00002c2 (FAIL)
sel=0x100 requested=0x70 returned=0x70 -> kr=0xe00002c2 (FAIL)
sel=0x100 requested=0x78 returned=0x78 -> kr=0 (OK)
sel=0x100 requested=0x80 returned=0x80 -> kr=0xe00002c2 (FAIL)
```

The production adapter now sends the producer's original 0x78 request first.
Only `kIOReturnBadArgument` from that exact read-only selector and shape permits
one 0x70 legacy retry. Thus 20F75 uses its native 0x78 ABI, the older 0x70
kernels retain compatibility, and unrelated errors or unknown call shapes pass
through unchanged. No AGX assertion, initialization error, or destructor was
bypassed.

## AGX type-0 resource shape

After the selector-0x100 negotiation was corrected, WindowServer advanced to
`AGX::Heap::Heap` and failed the first 64-KiB type-0 `ResCreate` with
`0xe00002be`. An iOS-native Metal heap probe and an injected, read-only
`IOConnectCallMethod` tracer captured the exact successful 20F75 producer
shape:

```text
+0x40=0
+0x48=0x10000
+0x50=0
+0x58=0xc38000000
result=0
```

The existing legacy adapter changed that same request to:

```text
+0x40=0x10000 +0x48=0 +0x50=0x38000000 +0x58=0
result=0xe00002be
```

The per-connection device-info result now selects the resource profile. A
native-0x78 connection preserves the producer's type-0 request byte-for-byte;
only the legacy-0x70 profile keeps the earlier layout translation. The first
production WindowServer create then recorded:

```text
AGXIOC type0 native-0x78 preserve #1: +0x40=0 +0x48=0x10000 +0x50=0 +0x58=0xc38000000
AGX_LIFE CREATE id=0x1 type=0 ... kr=0
```

This is a negotiated per-user-client invariant, not a device-model or OS-build
conditional. The retained legacy retry/profile is covered by focused tests so
the M1/iPadOS 16.3 path does not inherit the 20F75 resource layout.

## Workspace generation ordering

Once WindowServer and all four Aqua workspace agents were live, the first
two-Space creation succeeded. The subsequent wallpaper helper, launched after
Dock had been reloaded against that catalog, stopped responding. A five-second
sample of the exact helper process recorded all 4,203 main-thread samples at:

```text
main
  +[_NSScreenConfiguration latestScreens]
    SLSDisplayChangedSeed
      SLSInitialize
        initDisplayMappings
          CGSScoreboard
            SLSServerPort
              get_session_port
                mach_msg_new
                  mach_msg2_trap
```

This disproved the earlier pre-`main` theory: the helper was in `main`, blocked
on the new SkyLight session-port lookup. A one-variable ordering A/B kept the
same bounded operations and checks, but applied the persistent wallpaper in
the responsive generation before reloading Dock. The cold-start trace then
completed all three postconditions:

```text
Native macOS desktop navigation topology ready: ... after=2
Native macOS desktop wallpaper ready.
Dock rebound to completed native desktop catalog ...
Desktop input route ready ...
```

No timeout was extended and no SkyLight result was fabricated. The same order
is used by cold start and WindowServer-dependent recovery; desktop repair also
persists the wallpaper before replacing Dock.
